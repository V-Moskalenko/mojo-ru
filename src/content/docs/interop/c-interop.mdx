На C написано почти всё, что лежит под современными программами:
системные вызовы, сжатие, шифрование, работа с изображениями и звуком.
Переписывать это незачем — Mojo умеет звать C напрямую.

В отличие от Python, здесь нет интерпретатора посередине, и вызов стоит
почти ничего. Зато и страховки нет почти никакой — об этом большая часть
главы.

## Функция из libc: `external_call`

Стандартная библиотека C уже подключена к любой программе на Mojo,
и звать её функции можно без подготовки:

```mojo
from std.ffi import external_call, c_int, c_double


def main():
    print(external_call["abs", c_int](c_int(-7)))
    print(external_call["sqrt", c_double](c_double(2.0)))
    print(external_call["getpid", c_int]() > 0)
```

<Result output={"7\n1.4142135623730951\nTrue"} />

В квадратных скобках — **имя** функции и **тип результата**, в круглых —
аргументы. Типы аргументов компилятор выводит сам из того, что вы
передали.

<Aside type="note" title="Откуда берутся `c_int` и `c_double`">
  Это типы, соответствующие типам C на вашей платформе. Все лежат
  в `std.ffi`:

  | Имя | Размер на Linux x86-64 | Что это в Mojo |
  | --- | --- | --- |
  | `c_char`, `c_uchar` | 1 байт | `Int8`, `UInt8` |
  | `c_short`, `c_ushort` | 2 байта | |
  | `c_int`, `c_uint` | 4 байта | `c_int` — это `Int32` |
  | `c_long`, `c_ulong` | 8 байт | **отдельный** тип |
  | `c_long_long`, `c_ulong_long` | 8 байт | |
  | `c_size_t` / `c_ssize_t` | 8 байт | `UInt` / `Int` |
  | `c_float`, `c_double` | 4 / 8 байт | `Float32`, `Float64` |

  Большинство из них — просто другие имена для типов Mojo. А вот `c_long`
  — самостоятельный тип, и молча в `Int64` он не превратится:

  ```text
  error: cannot implicitly convert 'Scalar[_c_long_dtype()]' value to 'Int64'
  ```

  Это сделано нарочно: размер `long` в C зависит от платформы, и язык
  не даёт на него неявно рассчитывать. Пишите `Int64(x)` явно.

  Имён `c_void` и `c_bool` в `std.ffi` нет.
</Aside>

## Строки: где кончается строка C

В C у строки нет длины. Строка — это адрес первого байта, а конец
отмечен нулевым байтом. Функция вроде `strlen` просто идёт по памяти,
пока не наткнётся на ноль.

У `String` в Mojo для этого есть специальный метод — он гарантирует,
что ноль на месте:

```mojo
from std.ffi import external_call, c_size_t


def main():
    var word = String("привет")
    var n = external_call["strlen", c_size_t](word.as_c_string_span().ptr())
    print(n, word.byte_length())
```

<Result output={"12 12"} />

Двенадцать, а не шесть: C считает байты, а каждая кириллическая буква
в UTF-8 занимает два. Ровно то же самое говорит `byte_length()` — подробно
об этом в главе [Строки](/basics/strings/).

### Ловушка: срез без нуля

Вот место, где легко получить неправильный ответ без единой ошибки.
Срез строки в Mojo не копирует данные — он указывает внутрь исходной
строки. И нуля после него нет:

```mojo
from std.ffi import external_call, c_size_t


def main():
    var text = String("abcdef")
    var view = text[byte=0:3]
    print(view, view.byte_length())
    print(external_call["strlen", c_size_t](view.unsafe_ptr()))
```

<Result output={"abc 3\n6"} />

Срез — три байта. А C насчитал шесть: после `abc` нуля нет, и `strlen`
пошёл дальше, в `def`, пока не нашёл ноль в конце исходной строки.

Здесь повезло: ноль нашёлся в пределах своей памяти. В другой раз
C прочитает чужие данные — или программа упадёт.

<Aside type="danger" title="Правило для строк">
  В C передавайте только **настоящую** строку и только через
  `as_c_string_span().ptr()`. Срез сначала превратите в строку:

  ```mojo
  var copy = String(view)
  external_call["strlen", c_size_t](copy.as_c_string_span().ptr())   # 3
  ```

  Метод `unsafe_ptr()` даёт указатель на байты, но **не обещает** нуля
  после них — именно поэтому в имени стоит `unsafe`.

  Одна тонкость: `as_c_string_span()` может дописать ноль, а значит,
  **меняет** строку. На неизменяемом аргументе он не вызовется:

  ```text
  error: invalid call to 'as_c_string_span': invalid use of mutating method on rvalue of type 'String'
  ```

  В функции, принимающей `s: String`, сначала сделайте копию —
  `var c = s`, — или объявите аргумент `mut`.
</Aside>

<Aside type="caution" title="Устаревшие имена">
  В коде до 1.1 встречается `as_c_string_slice()` — компилятор просит
  заменить его на `as_c_string_span()`. А метод `unsafe_ptr()` у того,
  что возвращает `as_c_string_span()`, называется просто `ptr()`:

  ```text
  warning: 'as_c_string_slice' is deprecated, use 'as_c_string_span' instead
  warning: 'unsafe_ptr' is deprecated, use 'ptr' instead
  ```
</Aside>

## Своя библиотека: `OwnedDLHandle`

Функции libc доступны сразу. Для остальных библиотек её нужно
загрузить. Пусть есть файл `vec.c`:

```c
#include <stddef.h>

double dot(const double *a, const double *b, size_t n) {
    double s = 0.0;
    for (size_t i = 0; i < n; i++) s += a[i] * b[i];
    return s;
}

int add(int a, int b) { return a + b; }
```

Собираем его в разделяемую библиотеку:

```bash
gcc -O2 -shared -fPIC vec.c -o libvec.so
```

И зовём из Mojo:

```mojo
from std.ffi import OwnedDLHandle, c_int, c_double, c_size_t


def use_library() raises:
    var lib = OwnedDLHandle("./libvec.so")

    var add = lib.get_function[c_int]("add")
    print(add(c_int(2), c_int(3)))

    var a: List[Float64] = [1.0, 2.0, 3.0]
    var b: List[Float64] = [4.0, 5.0, 6.0]
    var dot = lib.get_function[c_double]("dot")
    print(dot(a.unsafe_ptr(), b.unsafe_ptr(), c_size_t(3)))
```

```text
5
32.0
```

Массивы передаются так же, как в C: указателем на первый элемент
и отдельно длиной. `List` хранит числа подряд, без обёрток, поэтому
его `unsafe_ptr()` — ровно то, чего ждёт функция на C.

<Aside type="note" title="Если что-то не нашлось">
  Отсутствие библиотеки или функции — обычное исключение, его можно
  поймать через `try`:

  ```text
  dlopen failed: ./no_such_lib.so: cannot open shared object file: No such file or directory
  symbol not found: no_such_func
  ```

  Поэтому функция, загружающая библиотеку, помечена `raises`.

  Проверить наличие функции без исключения можно заранее:
  `lib.check_symbol("add")` вернёт `True` или `False`. А для разового
  вызова `get_function` можно пропустить — `lib.call["add", c_int](...)`
  найдёт функцию и сразу вызовет её.
</Aside>

<Aside type="caution" title="`DLHandle` больше нет">
  В старых примерах библиотеку открывают через `DLHandle`, а тип функции
  целиком передают в `get_function`. В 1.1 остался только
  `OwnedDLHandle`, а в квадратных скобках указывается один лишь **тип
  результата** — типы аргументов выводятся при вызове.
</Aside>

## Самое опасное: компилятор вам верит

Вот главное, что нужно знать о вызове C. Mojo **не видит** исходник
функции на C и не может проверить, правильно ли вы описали её тип.
Что вы написали — тому он и верит.

Функция `dot` возвращает `double`. Ошибёмся и объявим `int`:

```mojo
var dot = lib.get_function[c_int]("dot")      # на самом деле double
print(dot(a.unsafe_ptr(), b.unsafe_ptr(), c_size_t(3)))
```

```text
3
```

Не `32`, не ошибка, не предупреждение — просто **три**. Программа
собралась, запустилась и спокойно выдала чушь.

### Откуда тройка

На x86-64 целый результат функция кладёт в регистр `rax`, дробный —
в `xmm0`. Функция `dot` честно положила ответ в `xmm0`, а мы попросили
прочитать `rax`. Что же там лежит? Дизассемблер показывает цикл
внутри `dot`:

```text
xor    %eax,%eax          ; i = 0 — счётчик цикла живёт в rax
...
add    $0x1,%rax          ; i += 1
cmp    %rax,%rdx          ; i == n ?
jne    ...
movapd %xmm1,%xmm0        ; ответ — в xmm0
```

После цикла счётчик `i` равен `n`, то есть трём. Его мы и прочитали.

И это число — не свойство программы, а случайность сборки. Та же
библиотека, собранная с другими флагами:

| Флаги `gcc` | n = 3 | n = 5 | n = 7 |
| --- | --- | --- | --- |
| `-O2` | 3 | 5 | 7 |
| `-O3 -march=native` | 2 | 4 | 6 |

Мусор не просто неправильный — он **правдоподобный**. Число, похожее
на размер данных, легко принять за осмысленный ответ.

### Аргументы тоже не проверяются

То же самое с типами аргументов. Функция `add` ждёт два `int`. Передадим
два дробных:

```mojo
var add = lib.get_function[c_int]("add")
print(add(Float64(2.0), Float64(3.0)))
```

```text
1069267464
```

Снова ни ошибки, ни предупреждения.

### Как защититься

Mojo сигнатуру не проверит — но проверить её можно, причём тем, кто
её знает точно: компилятором C, по настоящему заголовочному файлу.

Пусть у библиотеки есть заголовок `vec.h`:

```c
#include <stddef.h>
double dot(const double *a, const double *b, size_t n);
int add(int a, int b);
```

Рядом кладём маленький файл, который повторяет **ту** сигнатуру, что мы
записали в Mojo:

```c
#include "vec.h"

_Static_assert(__builtin_types_compatible_p(__typeof__(dot),
    double(const double *, const double *, size_t)),
    "dot: signature mismatch");
```

```bash
gcc -fsyntax-only check_signatures.c
```

Совпало — тишина. Ошиблись, написав `int` вместо `double`, — сборка
падает:

```text
error: static assertion failed: "dot: signature mismatch"
```

Такой файл стоит держать рядом с обёрткой и прогонять в CI: если
библиотека обновится и сигнатура изменится, узнаете сразу.

<Aside type="danger" title="И всё равно — прогон на известных данных">
  Проверка через заголовок ловит ошибку в **объявлении**. Но не ловит,
  если вы передали не тот массив, перепутали порядок аргументов или
  неверно поняли, что функция считает.

  Поэтому вторая защита обязательна — та же, что и во всём курсе: первым
  делом прогнать обёртку на данных, где ответ известен заранее.
</Aside>

## Сколько стоит вызов

В главе [Вызов Python из Mojo](/interop/python-from-mojo/) переход
границы стоил около 300 наносекунд. Для C тот же замер — тысяча
вызовов функции `add` из своей библиотеки — даёт:

| Куда | Наносекунд на вызов |
| --- | --- |
| функция из библиотеки на C | ≈ 2 |
| функция на Python | ≈ 300 |

Разница — **примерно в полтораста раз**. Вызов C — это обычный машинный
переход по адресу: ни упаковки в объекты, ни интерпретатора.

Поэтому правило «не зовите в горячем цикле» для C почти не действует:
пару наносекунд на вызов можно себе позволить там, где триста — уже
нельзя.

<Aside type="note" title="Почему не сравниваем с «нативным» кодом">
  Соблазнительно сравнить вызов `add` из C со сложением прямо на Mojo.
  Но простой цикл сложений компилятор вправе свернуть в формулу — мы
  видели это в главе [Как честно мерить скорость](/performance/benchmarking/).
  Вызов через библиотеку свернуть нельзя, и сравнение вышло бы нечестным.
  Поэтому здесь — только абсолютная цена вызова.
</Aside>

<Aside type="tip" title="Когда звать C">
  - Нужная библиотека уже написана на C, и переписывать её незачем:
    сжатие, форматы файлов, криптография, системные вызовы.
  - Нужен системный вызов, для которого в стандартной библиотеке Mojo
    ещё нет обёртки.

  И не нужно — ради скорости. Код на Mojo и так компилируется в машинные
  команды; переписывать на C то, что можно написать на Mojo, — значит
  потерять проверки типов и ничего не выиграть.
</Aside>

<Quiz>
  <QuizItem q="Что указывается в квадратных скобках `external_call[...]`, а что — в круглых?">
    В квадратных — имя функции и тип результата: `external_call["sqrt",
    c_double]`. В круглых — аргументы; их типы компилятор выводит сам.
    Тип результата вывести нельзя: Mojo не видит исходник функции на C.
  </QuizItem>
  <QuizItem q="Почему `strlen` для строки «привет» возвращает 12, а не 6?">
    Потому что C считает байты, а не символы. В UTF-8 каждая кириллическая
    буква занимает два байта. Mojo говорит то же самое через
    `byte_length()`.
  </QuizItem>
  <QuizItem q="Срез `text[byte=0:3]` от строки «abcdef» передали в `strlen` через `unsafe_ptr()` и получили 6. Почему?">
    Срез не копирует данные, а указывает внутрь исходной строки,
    и после `abc` нуля нет. `strlen` идёт по памяти до первого нуля —
    до конца `abcdef`. Правильно: превратить срез в строку `String(view)`
    и передать через `as_c_string_span().ptr()`.
  </QuizItem>
  <QuizItem q="Функцию, возвращающую `double`, по ошибке объявили с `c_int`. Что скажет компилятор?">
    Ничего. Mojo не видит исходник на C и верит объявлению. Программа
    соберётся и вернёт мусор — в нашем замере `3` вместо `32.0`: мы
    прочитали регистр `rax`, где лежал счётчик цикла функции. С другими
    флагами сборки число будет другим. Ловится это двумя способами:
    проверкой сигнатуры компилятором C по заголовку и прогоном на данных
    с известным ответом.
  </QuizItem>
  <QuizItem q="Как проверить, что сигнатура в Mojo совпадает с настоящей?">
    Компилятором C: в отдельном файле подключить настоящий заголовок
    и написать `_Static_assert(__builtin_types_compatible_p(__typeof__(f),
    тип_из_Mojo), "...")`. Команда `gcc -fsyntax-only` упадёт, если
    сигнатуры разошлись. Такую проверку стоит держать в CI.
  </QuizItem>
  <QuizItem q="Можно ли звать функцию на C внутри горячего цикла?">
    Как правило, да. Вызов стоит около двух наносекунд — это обычный
    машинный переход, без интерпретатора. Для сравнения, вызов Python
    стоит около трёхсот. Правило «не пересекать границу в цикле»
    относится к Python, а не к C.
  </QuizItem>
</Quiz>
