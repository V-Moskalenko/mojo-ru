В прошлой главе мы выяснили, что компилятор умеет выполнять ваш код.
Теперь разберёмся, что именно он готов посчитать, где проходит граница
и что делать, когда посчитанное нужно перенести в работающую программу.

## Считается почти любой код

Компилятору не нужны специальные функции. Годится обычная — с циклами,
ветвлениями, рекурсией:

```mojo
def triangular(n: Int) -> Int:
    var total = 0
    for value in range(1, n + 1):
        total += value
    return total


comptime SIZE = triangular(4)


def main():
    print(SIZE)
```

<Result output={"10"} />

Строки тоже считаются:

```mojo
def join_names() -> String:
    var result = String("")
    for name in ["раз", "два"]:
        result += name + " "
    return result


comptime GREETING = join_names()


def main():
    print(GREETING)
```

<Result output={"раз два "} />

## Таблица, посчитанная при сборке

Классический приём: заранее заполненная таблица вместо вычислений
во время работы.

```mojo
def build_powers() -> InlineArray[Int, 8]:
    var table = InlineArray[Int, 8](fill=0)
    var value = 1
    for index in range(8):
        table[index] = value
        value *= 2
    return table^


comptime POWERS = build_powers()
comptime LARGEST = POWERS[7]


def main():
    print(LARGEST)
```

<Result output={"128"} />

Ни цикла, ни умножений в готовой программе нет — там стоит `128`.

<Aside type="note" title="Почему `return table^`">
  `InlineArray` не копируется неявно, поэтому вернуть его из функции
  можно только передачей владения. Без сигила компилятор напомнит:

  ```text
  error: value of type 'Array[Int, Int(8)]' cannot be implicitly copied, it does not conform to 'ImplicitlyCopyable'
  ```

  Подробности — в главе [Копирование и перемещение](/ownership/copy-move/).
</Aside>

<Aside type="tip" title="Почему в ошибке написано `Array`, а не `InlineArray`">
  Это один и тот же тип. Настоящее имя — `Array`, а `InlineArray` оставлено
  как переходное имя для кода, написанного до 1.0. Проверяется в одну
  строку: значение типа `InlineArray[Int, 3]` спокойно присваивается
  переменной, объявленной как `Array[Int, 3]`.

  Так что можно писать и короче:

  ```mojo
  comptime SCALE: Array[Int, 5] = [1, 1024, 1048576, 1073741824, 1099511627776]
  ```

  Заодно объясняется и `Int(8)` в тексте ошибки: длина — это параметр,
  и компилятор печатает его так, как он выглядит внутри — обёрнутым в тип.
</Aside>

## `comptime assert`: проверка, которая не доживает до запуска

Обычный `assert` проверяет условие во время работы. `comptime assert`
проверяет его при сборке — и если условие ложно, программа просто
не соберётся:

```mojo
def main():
    comptime N = 5
    comptime assert N > 0, "N должно быть положительным"
    print(N)
```

<Result output={"5"} />

Поменяйте `5` на `-5`, и компилятор откажется собирать:

<CompilerError msg="error: function instantiation failed">
  <Fragment slot="meaning">
    Вычисление при сборке не удалось. Само по себе это сообщение
    ничего не объясняет — причину называет строка `note:` под ним.
    Для проваленной проверки там будет ваше сообщение:

    ```text
    note: constraint failed: N должно быть положительным
    ```

    Плюс предупреждение о том, что код после проверки недостижим.
  </Fragment>
  <Fragment slot="fix">
    Ошибка не в проверке, а в значении: либо исправьте его, либо
    ослабьте условие, если оно оказалось слишком строгим.
  </Fragment>
</CompilerError>

<Aside type="note" title="Это сообщение общее, а не про `assert`">
  `function instantiation failed` появляется при любом провале вычисления
  на этапе сборки. Например, если внутри comptime-функции произошёл выход
  за границы списка, верхняя строка будет той же, а причину назовут
  следующие:

  ```text
  note: failed to compile-time evaluate function call
  note: failed to interpret function @pick(...)
  ```

  Так что читать нужно не заголовок, а `note` под ним.
</Aside>

Обратите внимание на текст сообщения: он ваш. Это главная причина писать
`comptime assert` — читатель ошибки получает объяснение на человеческом
языке, а не разбирается во внутренностях шаблонов.

## Граница: чего компилятор считать не будет

На этапе сборки не существует внешнего мира. Официальное руководство
перечисляет четыре вещи, которые компилятор выполнять отказывается:

| Что нельзя | Почему |
| --- | --- |
| файловый ввод-вывод | файлов на этапе сборки нет |
| вызовы внешних функций (FFI) | чужую библиотеку компилятор не загружает |
| функции, помеченные `raises` | обрабатывать исключение при сборке некому |
| выполнение на GPU | comptime-код в GPU-программе считается на CPU |

Первые две категории пересекаются с третьей, но **не сводятся** к ней —
и ошибки у них разные. Это важно: по тексту сообщения вы поймёте,
на что именно наткнулись.

**`raises` отсекается сразу, ещё при разборе кода:**

<CompilerError msg="error: cannot call raising function in comptime initializer">
  <Fragment slot="meaning">
    Функция помечена `raises`, а на этапе сборки обрабатывать исключения
    некому — компилятор отказывается её выполнять, даже не пытаясь.
  </Fragment>
  <Fragment slot="fix">
    Если функция и правда может не справиться — считайте её во время
    работы программы. Если `raises` попало в сигнатуру случайно, уберите
    его: часто достаточно не вызывать внутри `Int(String(...))` или
    обращение к словарю по ключу.
  </Fragment>
</CompilerError>

Сюда же попадает почти весь ввод-вывод: `open()` бросает, разбор строки
в число бросает.

**FFI разбирается нормально, но спотыкается при вычислении.** Функция
с `external_call` не помечена `raises`, поэтому до первой ошибки дело
доходит позже — когда компилятор пытается её выполнить:

```text
error: function instantiation failed
note: failed to compile-time evaluate function call
note: failed to interpret function @try_ffi()
note: failed to interpret operation pop.external_call{func: "abs" ...}
```

Последняя строка и есть диагноз: дошли до чужого кода, а исполнить его
нечем.

Считать можно то, что зависит только от самих значений.

<Aside type="tip" title="Как убедиться, что вычисление правда было на сборке">
  Поставьте `print` внутрь функции, которую вызываете в `comptime`.
  Соберите программу командой `mojo build`: строка напечатается **прямо
  во время сборки**. Запустите получившийся файл — её там уже не будет.

  ```text
  $ mojo build p.mojo -o p
  считаю 21                ← напечаталось при сборке
  $ ./p
  результат: 42            ← а тут остался только результат
  ```

  Это самый наглядный способ увидеть две фазы своими глазами.
</Aside>

## Материализация: перенос значения в работающую программу

Пока значение живёт только на этапе сборки, оно ничего не стоит. Но иногда
его нужно отдать в обычный код — например, использовать таблицу как
изменяемый массив. Это называется **материализацией**.

Критерий у неё ровно один — трейт `ImplicitlyCopyable`. Что копируется
неявно, то и материализуется само: `Int`, `Float64`, `Bool` и, что важно,
`String`. Всё остальное — `InlineArray`, `List`, ваши собственные
`Copyable`-типы — компилятор потребует перенести явно:

<CompilerError msg="error: cannot materialize comptime value of type 'Array[Int, Int(8)]' to runtime because it is not 'ImplicitlyCopyable'">
  <Fragment slot="meaning">
    Вы попросили перенести в работающую программу значение, которое неявно
    не копируется. Компилятор не делает такого молча — по той же причине,
    по которой не копирует списки молча.
  </Fragment>
  <Fragment slot="fix">
    Компилятор подсказывает решение прямо в тексте:

    ```text
    note: use 'materialize' to explicitly materialize the value
    ```

    Пишем `var table = materialize[POWERS]()` — и дальше это обычный
    массив, живущий во время работы программы.
  </Fragment>
</CompilerError>

<Aside type="caution" title="Индексация — это уже этап выполнения">
  Ловушка, на которую легко наступить: обращение `POWERS[3]` внутри
  обычного кода — это **уже работа во время выполнения**, и компилятор
  потребует материализацию.

  ```mojo
  comptime THIRD = POWERS[3]   # посчитано при сборке
  var value = POWERS[3]        # ошибка: нужна материализация
  ```

  Правило простое: если результат нужен обычному коду — либо объявите
  его через `comptime`, либо материализуйте контейнер целиком.
</Aside>

### Материализация не бесплатна

Требование писать `materialize` явно — не формальность. Руководство
объясняет замысел прямо: язык заставляет вас явно материализовать то,
что материализовать дорого, «чтобы вы управляли моментом, когда программа
выделяет ресурсы».

Смотрите, что происходит с таблицей:

```mojo
def peek(index: Int) -> Int:
    var table = materialize[POWERS]()   # копия — при каждом вызове
    return table[index]
```

Функцию вызвали миллион раз — таблицу собрали миллион раз. Смысл
предвычисления при этом теряется целиком.

### `global_constant`: таблица, которую переносить не нужно

Для таблиц поиска есть правильный инструмент. `global_constant` кладёт
посчитанное значение в статическую память программы — один раз, при
сборке, — и возвращает на него ссылку:

```mojo
from std.builtin.globals import global_constant


def peek(index: Int) -> Int:
    ref table = global_constant[POWERS]()
    return table[index]
```

Ключевое слово здесь — `ref`. Оно связывает именно ссылку; напишете `var`,
и копия вернётся обратно.

<Aside type="note" title="Ограничение">
  Так пока можно только с самодостаточными значениями — теми, что
  не содержат указателей на другую память. Массив чисел или строковых
  литералов подходит; `List`, который хранит данные в куче, — нет.
</Aside>

## Ещё две формы

**Подвыражение прямо в коде.** Если хочется посчитать что-то при сборке,
не заводя отдельного имени:

```mojo
def triangular(n: Int) -> Int:
    var total = 0
    for value in range(1, n + 1):
        total += value
    return total


def main():
    var precomputed = comptime (triangular(100))
    print(precomputed)
```

<Result output={"5050"} />

**Параметризованное значение.** Своё для каждого аргумента, вычисляется
при сборке:

```mojo
comptime Doubled[value: Int]: Int = value * 2


def main():
    print(Doubled[21])
```

<Result output={"42"} />

Это похоже на функцию, но живёт целиком на этапе компиляции: в программе
от неё остаётся только результат. Подробный разговор о параметрах —
в следующей главе, [Параметризация](/meta/parameters/).

**Имя для типа.** `comptime` объявляет не только числа и строки. Тип —
тоже значение этапа сборки, и ему можно дать короткое имя:

```mojo
comptime Pair = Tuple[Int, String]


def main():
    var p = Pair(1, String("раз"))
    print(p[0], p[1])
```

<Result output={"1 раз"} />

Это ровно то, чем в Python занимается `TypeAlias`, — но здесь имя исчезает
при сборке, а не живёт в памяти как объект.

<Aside type="note" title="`comptime var` не бывает">
  Соблазн написать `comptime var counter = 0` и накапливать значение
  в `comptime for` есть у всех. Компилятор откажет:

  ```text
  error: 'comptime' cannot be used with 'var'
  ```

  Значение на этапе сборки — именно значение, а не переменная. Накопление
  оформляют функцией, которая считает и возвращает результат, — как
  `triangular` в начале главы.
</Aside>

## Всё вместе

Одна маленькая задача: перевести число байт в человекочитаемый вид.
Таблица множителей — степени 1024 — считается при сборке, а в программе
живёт как статическая константа, к которой обращаются по ссылке.

<Quiz>
  <QuizItem q="Какие функции компилятор может выполнить на этапе сборки?">
    Почти любые — с циклами, рекурсией, строками. Отказывается он от
    четырёх вещей: файлового ввода-вывода, вызовов внешних библиотек (FFI),
    функций с `raises` и выполнения на GPU. Причём `raises` отсекается
    сразу при разборе кода, а FFI — уже при вычислении, и сообщения
    у них разные.
  </QuizItem>
  <QuizItem q="Зачем `comptime assert`, если есть обычная проверка?">
    Она срабатывает при сборке, а не при запуске, и печатает ваше
    сообщение: `note: constraint failed: ваш текст`. Тот, кто неправильно
    воспользовался вашим кодом, получает объяснение по-человечески
    и до того, как программа вообще собралась.
  </QuizItem>
  <QuizItem q="Что такое материализация?">
    Перенос вычисленного при сборке значения в работающую программу.
    Для всего, что копируется неявно, происходит сама — включая `String`.
    Для остального требует явного `materialize[...]()`: компилятор
    не переносит молча то, что не копируется неявно.
  </QuizItem>
  <QuizItem q="Почему `var value = POWERS[3]` требует материализации, а `comptime THIRD = POWERS[3]` — нет?">
    Потому что во втором случае индексация происходит при сборке
    и в программу попадает готовое число. В первом результат нужен
    обычному коду — а значит, таблицу приходится переносить
    в работающую программу.
  </QuizItem>
  <QuizItem q="Функция `loud(n)` печатает «считаю n» и возвращает `n * 2`. Её результат объявлен как `comptime VALUE = loud(21)`, а `main` печатает `результат: VALUE`. Что вы увидите при сборке, а что при запуске?">
    При сборке — строку `считаю 21`. При запуске — только
    `результат: 42`. Функция отработала один раз, внутри компилятора,
    и в программу попало готовое число: ни вызова, ни умножения там нет.
    Проверяется руками: `mojo build` покажет первую строку, запуск
    собранного файла — вторую.
  </QuizItem>
  <QuizItem q="Функция `peek` вызывается миллион раз и внутри делает `materialize[POWERS]()`. В чём беда?">
    Таблица собирается заново при каждом вызове — предвычисление
    не даёт ничего. Для таблиц поиска нужен `global_constant`:
    он кладёт значение в статическую память один раз, а `ref` связывает
    ссылку на него без копии.
  </QuizItem>
</Quiz>
