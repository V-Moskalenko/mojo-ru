У программы на Python одна фаза жизни: запустили — работает. У программы
на Mojo их две, и это меняет способ думать о коде.

**Фаза сборки.** Компилятор читает исходник, вычисляет всё, что можно
вычислить заранее, разворачивает циклы, выбрасывает недостижимые ветки
и генерирует машинный код.

**Фаза выполнения.** Программа запускается и делает то, что осталось.

Метапрограммирование — это умение переносить работу из второй фазы
в первую. Всё, что посчитано при сборке, во время работы уже бесплатно.

## Компилятор различает эти фазы строго

Проверить это можно за пять секунд — код ниже нужно положить внутрь
функции, на верхнем уровне переменных в Mojo не бывает:

```mojo
var size = 4
var buffer = InlineArray[Int, size](fill=0)   # ошибка
```

<CompilerError msg="error: cannot use a dynamic value in a parameter list">
  <Fragment slot="meaning">
    `InlineArray` хранит данные прямо в себе, поэтому его длина должна быть
    известна компилятору — иначе он не знает, сколько места отвести.
    А `size` здесь обычная переменная: её значение появится только
    при запуске.
  </Fragment>
  <Fragment slot="fix">
    Объявите значение как вычисляемое при сборке:

    ```mojo
    def main():
        comptime size = 4
        var buffer = InlineArray[Int, size](fill=0)
    ```
  </Fragment>
</CompilerError>

Это и есть граница двух фаз. Всё в квадратных скобках живёт в первой,
всё в круглых — во второй.

## `comptime`: значение, посчитанное при сборке

Слово `comptime` объявляет значение, которое компилятор вычисляет сам:

```mojo
def triangular(n: Int) -> Int:
    var total = 0
    for value in range(1, n + 1):
        total += value
    return total


comptime SIZE = triangular(4)


def main():
    print(SIZE)
```

<Result output={"10"} />

Обратите внимание: `triangular` — совершенно обычная функция, никак
не помеченная. Компилятор просто выполнил её сам и подставил в программу
готовое число. В собранном коде цикла нет — там `10`.

Обычная — но не любая. У вычислений на сборке есть жёсткая граница:
на этапе компиляции не существует ни файлов, ни сети, ни внешних библиотек.
Функция, помеченная `raises`, отвергается сразу:

```text
error: cannot call raising function in comptime initializer
```

А поскольку `open()` и разбор строки в число умеют бросать исключения,
вместе с ними отпадает и весь ввод-вывод. Но `raises` — не единственный
запрет: вызовы внешних библиотек и код для GPU компилятор тоже
не выполняет. Полный список и разные тексты ошибок — в главе
[Вычисления на этапе компиляции](/meta/comptime/).

<Aside type="note" title="Проверить, что вычисление правда произошло на сборке">
  Поставьте `print` внутрь функции, которую вызываете в `comptime`,
  и соберите программу через `mojo build`. Строка напечатается **прямо
  во время сборки**, а в выводе собранного файла её уже не будет: она
  отработала раньше.
</Aside>

<Aside type="caution" title="`alias` переименован в `comptime`">
  До 1.0 значение этапа сборки объявляли словом `alias`. Оно всё ещё
  работает, но компилятор просит перейти на новое:

  ```text
  warning: 'alias' is deprecated; use 'comptime'
  ```

  Знать об этом нужно не ради своего кода, а ради чужого: почти всё,
  что написано о Mojo до 1.0 — статьи, ответы на форумах, примеры
  в библиотеках, — использует `alias`. Встретив его, читайте `comptime`.
</Aside>

<Aside type="tip" title="Это не то же самое, что константа в Python">
  В Python `SIZE = 10` — это переменная, которую по соглашению не меняют,
  но она живёт во время выполнения и занимает память.

  `comptime SIZE = 10` в Mojo не занимает ничего: к моменту запуска этого
  имени уже не существует, вместо него в коде стоит число. Память появится
  только если вы сами перенесёте значение в обычную переменную —
  это называется материализацией, и о ней будет отдельный разговор.
</Aside>

## `comptime if`: ветка выбирается при сборке

Обычный `if` проверяет условие каждый раз при выполнении. `comptime if`
проверяет его один раз при сборке — и в готовую программу попадает только
выбранная ветка:

```mojo
def label[verbose: Bool]() -> String:
    comptime if verbose:
        return String("подробный режим")
    else:
        return String("кратко")


def main():
    print(label[True]())
    print(label[False]())
```

<Result output={"подробный режим\nкратко"} />

Компилятор собрал **две разные функции**: в одной осталась только первая
строка, в другой — только вторая. Никакой проверки условия во время работы
не происходит — это видно и в собранном бинарнике, куда попадает текст
только выбранной ветки.

<Aside type="caution" title="Отброшенная ветка всё равно проверяется">
  `comptime if` — не `#ifdef` из C. Ветка, которая не попадёт в программу,
  всё равно разбирается и проверяется на типы: написать в ней что попало
  не выйдет.

  ```text
  error: 'Int' value has no attribute 'no_such_method'
  ```

  Отключается только генерация кода, а не проверка. Обычно это и хорошо:
  ошибку в редко используемой ветке вы увидите сразу, а не через полгода.
</Aside>

## `comptime for`: цикл разворачивается при сборке

```mojo
def banner[times: Int](text: String):
    comptime for index in range(times):
        print(index, text)


def main():
    banner[3]("повтор")
```

<Result output={"0 повтор\n1 повтор\n2 повтор"} />

В собранной программе здесь не цикл, а три подряд идущих вызова `print`.
Счётчика нет, проверки условия нет, перехода назад нет.

<Aside type="caution" title="`@parameter if` и `@parameter for` устарели">
  Раньше эти конструкции писались декоратором `@parameter` перед `if`
  или `for`. Так они выглядят почти во всех статьях, ответах на форумах
  и в учебниках, написанных до 1.0. Код соберётся, но компилятор скажет:

  ```text
  warning: '@parameter for' is deprecated; use 'comptime for'
  warning: '@parameter if' is deprecated; use 'comptime if'
  ```

  Заменяйте на `comptime if` и `comptime for`.

  Важно не перепутать: устарели именно эти две формы. Сам декоратор
  `@parameter` перед **вложенной функцией** — совсем другая конструкция,
  она жива и предупреждений не вызывает. О ней речь пойдёт в разделе
  [Производительность](/performance/closures/).
</Aside>

## Что это даёт

<PyMojo>
  <Fragment slot="python">
```python
def area(shape, size):
    if shape == "круг":
        return 3.14159 * size * size
    return size * size

# проверка shape происходит
# при каждом вызове
```
  </Fragment>
  <Fragment slot="mojo">
```mojo
def area[circle: Bool](size: Float64) -> Float64:
    comptime if circle:
        return 3.14159 * size * size
    return size * size

# проверки нет вовсе:
# собраны две отдельные функции
```
  </Fragment>
  <Fragment slot="note">
    В Python сравнение строк выполняется миллион раз, если функцию вызвали
    миллион раз. В Mojo оно выполнится один раз — при сборке.
  </Fragment>
</PyMojo>

Выигрыш складывается из трёх вещей:

- **нет проверок**, которые всё равно всегда дают один и тот же ответ;
- **нет циклов** с известным заранее числом шагов;
- **компилятор видит больше**: зная длину числом, он вправе развернуть
  обработку или векторизовать её. В отличие от первых двух пунктов это
  не гарантия, а возможность — как повезёт с оптимизатором.

## Чем за это платят

Метапрограммирование — не бесплатный обед.

| Что растёт | Почему |
| --- | --- |
| Время сборки | компилятор выполняет ваш код, а не только переводит его |
| Сложность сообщений об ошибках | ошибка возникает в сгенерированном коде, а не в написанном |

Второй пункт — главная причина не увлекаться. Параметр там, где хватило
бы обычного аргумента, усложняет чтение кода и ухудшает диагностику,
а выигрыша не даёт.

Часто добавляют третий пункт — размер программы: под каждый набор
параметров генерируется своя копия функции. Механизм именно такой,
но результат неочевиден: копия, в которой всё свернулось в константы,
бывает **меньше** общей версии. Мы это измерили — цифры и оба исхода
в главе [Параметризация](/meta/parameters/#чем-за-это-платят).

<Aside type="note" title="Правило на каждый день">
  Параметр оправдан, когда значение **действительно** известно заранее
  и от него зависит генерируемый код: размер буфера, тип элемента,
  ширина SIMD-вектора, включённость отладочных проверок.

  Во всех остальных случаях берите обычный аргумент.
</Aside>

<Quiz>
  <QuizItem q="Какие две фазы жизни есть у программы на Mojo?">
    Сборка и выполнение. На сборке компилятор вычисляет всё, что может,
    разворачивает циклы и выбрасывает недостижимые ветки; на выполнении
    программа делает то, что осталось. Метапрограммирование — это перенос
    работы из второй фазы в первую.
  </QuizItem>
  <QuizItem q="Почему `InlineArray[Int, size]` с обычной переменной `size` не компилируется?">
    Потому что в квадратных скобках живут значения, известные на этапе
    сборки, а обычная переменная получит значение только при запуске.
    Компилятор так и говорит: `cannot use a dynamic value in a parameter
    list`. Решение — объявить `comptime size = 4`.
  </QuizItem>
  <QuizItem q="Чем `comptime if` отличается от обычного `if`?">
    Обычный `if` проверяет условие при каждом выполнении. `comptime if`
    проверяется один раз при сборке, и в программу попадает только
    выбранная ветка — проверки во время работы не остаётся вовсе.
  </QuizItem>
  <QuizItem q="Что делать, если в чужом коде встретился `@parameter if` или `alias`?">
    Заменить на `comptime if` и `comptime`. Старые формы ещё работают,
    но компилятор выдаёт предупреждение об устаревании. То же и
    с `@parameter for`. Это стоит держать в голове при чтении любых
    материалов о Mojo, написанных до 1.0, — а таких большинство.
  </QuizItem>
</Quiz>
