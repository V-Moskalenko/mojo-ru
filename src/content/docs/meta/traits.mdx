Параметр типа `[T: ...]` мы уже писали, но всегда с готовым требованием
из стандартной библиотеки. Пора научиться объявлять требования самим.

## Зачем это нужно

В Python обобщённый код держится на утиной типизации: раз у объекта есть
метод `price()`, значит подойдёт. Ошибка вылезает при запуске, у клиента.

Mojo требует, чтобы обещание было записано в коде. **Трейт** — это
и есть такая запись: список того, что тип обязан уметь.

<PyMojo>
  <Fragment slot="python">
```python
def average(sensors):
    # надеемся, что у всех
    # есть .read()
    return sum(s.read()
               for s in sensors) / len(sensors)
```
  </Fragment>
  <Fragment slot="mojo">
```mojo
def average[T: Sensor](
    items: List[T]
) -> Float64:
    # компилятор проверил,
    # что .read() есть
    ...
```
  </Fragment>
  <Fragment slot="note">
    В Python «есть ли метод» выясняется при вызове. В Mojo — при сборке,
    и не у вас, а у того, кто попытался подсунуть неподходящий тип.
    Но есть и цена: питоновский список может быть разнородным,
    а `List[T]` — нет. Об этом ниже.
  </Fragment>
</PyMojo>

## Объявить и реализовать

Трейт объявляется словом `trait`, а `...` отмечает метод как
обязательный:

```mojo
trait Sensor:
    def read(self) -> Float64:
        ...


@fieldwise_init
struct Capacitive(Copyable, Sensor):
    def read(self) -> Float64:
        return 21.5


def average[T: Sensor](sensor: T, samples: Int) -> Float64:
    var total = 0.0
    for _ in range(samples):
        total += sensor.read()
    return total / Float64(samples)


def main():
    print(average(Capacitive(), 4))
```

<Result output={"21.5"} />

Соответствие объявляется в скобках после имени структуры — там же, где
`Copyable`. Никакой разницы между «своими» и «библиотечными» трейтами нет.

## Утиной типизации нет

Это главное отличие от Python, и на нём спотыкаются. Мало **иметь**
нужный метод — нужно **объявить** трейт:

```mojo
@fieldwise_init
struct Rogue(Copyable):
    def read(self) -> Float64:      # метод есть...
        return 1.0                  # ...но Sensor не объявлен
```

<CompilerError msg="error: invalid call to 'average': value passed to 'sensor' cannot be converted from 'Rogue' to 'T', argument type 'Rogue' does not conform to trait 'Sensor'">
  <Fragment slot="meaning">
    Компилятор не угадывает намерения по именам методов. Совпадение
    сигнатуры для него ничего не значит — значение имеет только явно
    объявленное соответствие.
  </Fragment>
  <Fragment slot="fix">
    Допишите трейт в список: `struct Rogue(Copyable, Sensor)`.
  </Fragment>
</CompilerError>

Строгость намеренная. Совпадение имён бывает случайным: `read()` у датчика
и `read()` у файла — разные вещи, и хорошо, когда компилятор не считает
их взаимозаменяемыми.

<Aside type="caution" title="Чужому типу трейт не добавить">
  Соответствие объявляется **там, где тип определён**. Дописать трейт
  к `Int` или к типу из чужой библиотеки нельзя — ни в Mojo 1.0, ни
  в планах. Это отличие от Rust с его `impl Trait for Type`.

  Обычный обход — обёртка: свой тип с полем нужного и объявленным
  трейтом.
</Aside>

## Реализация по умолчанию

Метод в трейте может иметь тело. Тогда он необязателен: кто хочет —
переопределит, кто не хочет — получит написанное в трейте. Такой метод
называют **реализацией по умолчанию**.

```mojo
trait Sensor:
    def read(self) -> Float64:
        ...

    def label(self) -> String:
        return String("датчик без имени")
```

Тип, реализовавший только `read`, всё равно соответствует `Sensor`
и получает `label` даром. Это способ расширять трейт, не ломая тех, кто
уже ему соответствует.

<Aside type="caution" title="Два трейта с одинаковым запасным методом">
  Если тип соответствует двум трейтам и оба дают реализацию метода
  с одним именем, компилятор выбирать не станет:

  ```text
  error: trait method requirement 'name' has conflicting default implementations in 'A' and 'B'; you must implement it manually
  ```

  Решение подсказано в самом тексте: написать метод в структуре явно.
</Aside>

<Aside type="tip" title="Как отличить обязательный метод от запасного">
  По телу. `...` — обязателен, всё остальное — реализация по умолчанию
  (в документации — *provided method*).
  Трейт, у которого нет ни одного требования, называется **маркерным**:
  он ничего не просит, а только помечает тип.

  ```mojo
  trait Marker:
      pass
  ```
</Aside>

## Что бывает, если требование не выполнено

<CompilerError msg="error: 'Broken' does not implement all requirements for 'Sensor'">
  <Fragment slot="meaning">
    Трейт — это всё или ничего: соответствующий тип обязан закрыть каждое
    требование. Какое именно не закрыто, компилятор говорит следующей
    строкой:

    ```text
    note: required function 'read' is not implemented
    note: trait 'Sensor' declared here
    ```
  </Fragment>
  <Fragment slot="fix">
    Реализуйте названный метод — или уберите трейт из списка, если тип
    ему и не должен соответствовать.
  </Fragment>
</CompilerError>

## Несколько трейтов сразу и трейт поверх трейта

**Несколько требований сразу** — через `&`:

```mojo
def average[T: Sensor & Movable](items: List[T]) -> Float64:
```

Второе требование здесь — не от вашей задачи, а от `List`: чтобы хранить
элементы, он должен уметь их перемещать. Мы уже встречали эту ситуацию
в главе [Параметризация](/meta/parameters/): компилятор просит
«свидетельство», которого в задаче не было.

**Имя для набора требований.** Если одна и та же связка нужна в разных
местах, ей дают имя обычным `comptime`:

```mojo
comptime SensorLike = Sensor & Movable


def average[T: SensorLike](items: List[T]) -> Float64:
    ...
```

Такое имя годится и в списке соответствия структуры:
`struct Precise(Copyable, SensorLike)`.

**Уточнение** — трейт, который включает другой:

```mojo
trait Calibratable(Sensor):
    def calibrate(mut self):
        ...
```

Всё, что соответствует `Calibratable`, автоматически годится и там, где
просят `Sensor`. Обратное неверно.

<Aside type="tip" title="`Some[...]` — когда имя типа не нужно">
  Если параметр типа используется ровно один раз, называть его незачем.
  Эти две записи означают одно и то же:

  ```mojo
  def show[T: Sensor](s: T):
      print(s.read())


  def show(s: Some[Sensor]):
      print(s.read())
  ```

  Вторая короче и читается ближе к человеческому «принимает какой-нибудь
  датчик». Имя нужно, когда тип упоминается дважды: в двух аргументах,
  в типе возврата или внутри тела.
</Aside>

## Что просить у типа: стандартные трейты

Своё требование стоит объявлять, только когда в библиотеке нет готового.
Вот те, что понадобятся в этой главе и рядом — каждая строка проверена
на компиляторе 1.0.0:

| Трейт | Что даёт | Что реализовать |
| --- | --- | --- |
| `Writable` | `print(x)` **и** `String(x)` | `write_to[W: Writer](self, mut writer: W)` |
| `Equatable` | `==` и `!=` | `__eq__` |
| `Comparable` | все шесть операторов сравнения | только `__lt__` |
| `Hashable` | хеш значения | `__hash__` |
| `Sized` | `len(x)` | `__len__` |
| `Boolable` | `if x:` | `__bool__` |
| `Intable` / `Floatable` | `Int(x)` / `Float64(x)` | `__int__` / `__float__` |
| `Defaultable` | создание без аргументов | `__init__(out self)` |

Трейты копирования — `Copyable`, `ImplicitlyCopyable` — подробно разобраны
в главе [Копирование и перемещение](/ownership/copy-move/); здесь они
ничем не отличаются от своих.

Полный список — в [справочнике](/reference/cheatsheet/).

<Aside type="tip" title="Три подарка, о которых стоит знать заранее">
  **`Comparable` требует только `__lt__`.** Остальные пять операторов
  — `>`, `==`, `!=`, `<=`, `>=` — приходят реализациями по умолчанию.
  Проверено: структура с единственным `__lt__` корректно отвечает
  на все шесть. В Python для того же зовут `functools.total_ordering`.

  **`Writable` даёт и печать, и строку.** Написали `write_to` — работает
  и `print(x)`, и `String(x)`. Отдельного трейта для строкового
  представления в 1.0 нет.

  **Многое пишется само.** Объявите трейт — и, если полей достаточно,
  компилятор синтезирует реализацию. Структура с полями `v: Int`
  и `name: String`, объявленная как `Writable`, но без единого метода,
  печатается как `M(v=5, name=привет)`. Так же синтезируются `copy()`,
  `__eq__` и `__hash__`.
</Aside>

<Aside type="caution" title="`Movable` объявлять обычно не нужно">
  Соответствие `Movable` у обычной структуры возникает само: её можно
  передавать через `^` и класть в `List`, ничего не объявляя. Это
  согласуется с правилом из главы
  [Копирование и перемещение](/ownership/copy-move/): перемещение
  доступно всегда, трейты управляют только копированием.

  Писать `Movable` в списке приходится в одном случае — когда
  **обобщённая функция** требует его от параметра: `[T: Sensor & Movable]`.
  Требование там идёт от `List`, а не от вашей задачи.
</Aside>

<Aside type="caution" title="Ключ словаря — это не только `Hashable`">
  Одного `Hashable` для `Dict` и `Set` не хватает. Компилятор называет
  полный набор сам:

  ```text
  note: 'KeyElement' is aka 'Equatable & Hashable & Movable'
  ```

  То есть ключ обязан ещё и сравниваться на равенство — иначе словарь
  не отличит коллизию хеша от совпадения ключей.
</Aside>

<Aside type="note" title="Имена трейтов, которых больше нет">
  В материалах, написанных до 1.0, постоянно встречаются `Stringable`,
  `Representable`, `EqualityComparable`, `GreaterThanComparable`,
  `CollectionElement`. Компилятор 1.0.0 ни одного из них не знает —
  все дают `error: use of unknown declaration`.

  Чем их заменять, собрано в главе
  [Что устарело](/python-to-mojo/outdated/). Короткая версия: вместо
  `Stringable` с `__str__` пишите `Writable` с `write_to`.
</Aside>

## Ассоциированные типы

Трейт может потребовать не только методы, но и **тип**, свой у каждого
реализующего:

```mojo
trait Container:
    comptime Element: AnyType

    def first(self) -> Self.Element:
        ...


@fieldwise_init
struct IntBox(Copyable, Container):
    comptime Element = Int
    var value: Int

    def first(self) -> Int:
        return self.value


def peek[C: Container](c: C) -> C.Element:
    return c.first()


def main():
    print(peek(IntBox(7)))
```

<Result output={"7"} />

Обратите внимание на `C.Element` в типе возврата: функция обещает вернуть
то, что лежит в контейнере, не зная заранее, что это. Так устроены
итераторы и коллекции в стандартной библиотеке.

<Aside type="caution" title="В руководстве написано `associatedtype` — не верьте">
  Официальное руководство объявляет ассоциированный тип отдельным словом:
  `associatedtype Element: Copyable`. Компилятор 1.0.0 такого не понимает
  и подсказывает правильную форму сам:

  ```text
  error: bare expressions must not appear within traits; use 'comptime' for an associated type or move this into a method body
  ```

  Пишите `comptime`. Требование к типу задаётся после двоеточия:
  `comptime Element: AnyType` — «любой тип», `comptime Element: Copyable`
  — «копируемый».
</Aside>

Точно так же трейт может потребовать **значение**:

```mojo
trait Unit:
    comptime name: StaticString
    comptime factor: Float64


@fieldwise_init
struct Foot(Copyable, Unit):
    comptime name = "фут"
    comptime factor = 0.3048


def describe[U: Unit]():
    print(U.name, "->", 2.0 * U.factor, "м")


def main():
    describe[Foot]()
```

<Result output={"фут -> 0.6096 м"} />

Здесь `Foot` не создаётся вовсе — тип работает как носитель констант,
и вся функция целиком считается при сборке.

## Один тип на вызов, а не любой из подходящих

Здесь питониста ждёт главное разочарование главы, и лучше встретить его
сейчас, чем в своём коде.

Обобщённая функция `average[T: Sensor]` не принимает «любой датчик».
Она собирается **отдельно под каждый конкретный `T`**. Поэтому список
разнородных датчиков составить нельзя:

<CompilerError msg="error: 'List' parameter 'T' has 'Movable' type, but value has type 'AnyTrait[Sensor]'">
  <Fragment slot="meaning">
    Вы написали `List[Sensor]`, то есть попросили список «чего угодно,
    что соответствует трейту». Но `List` хранит значения одного типа
    известного размера, а трейт — это требование, а не тип.
  </Fragment>
  <Fragment slot="fix">
    Держите однородные списки и вызывайте обобщённую функцию для каждого
    отдельно — так и сделано в примере ниже. Механизма «список разных
    типов за общим интерфейсом» в Mojo 1.0 нет.
  </Fragment>
</CompilerError>

Вот в чём разница с Python на самом деле: там `[book, coffee]` — обычное
дело, потому что каждый элемент несёт свой тип с собой и метод ищется
при вызове. В Mojo тип известен заранее и в списке он один.

## Всё вместе

Прайс-лист: у книг и кофе общее ровно одно — цена.

<Code code={pricing} lang="mojo" title="pricing.mojo" />

<Result output={"книги:\n   Мойо — 890 ₽ | на складе\n   Расты — 1250 ₽ | на складе\nитого: 2140 ₽\nкофе:\n   250 г — 875 ₽ | под заказ\n   1000 г — 3500 ₽ | под заказ\nитого: 4375 ₽\nдороже ли кофе книг: True"} />

Три вещи, ради которых стоит перечитать пример:

- `total` написан **один раз**, а работает и с книгами, и с кофе;
- `Coffee` не реализует `in_stock` — печатается «под заказ» из трейта;
- списки держатся раздельно, и это не лень автора, а следствие
  устройства языка.

<Aside type="note" title="Мелочь, на которой легко споткнуться">
  В примере списки объявлены с явным типом:

  ```mojo
  var books: List[Book] = [Book("Мойо", 89000)]
  ```

  Голый литерал `[...]` даёт не `List`, а `Array` — контейнер
  фиксированной длины. Функция, объявленная как принимающая `List[T]`,
  его не примет:

  ```text
  error: invalid call to 'total': value passed to 'items' cannot be converted from 'Array[Book, Int(2)]' to 'List[T]', it depends on an unresolved parameter 'T'
  ```
</Aside>

<Quiz>
  <QuizItem q="Функция `total[T: Priced]` не собирается: компилятор просит «evidence for conforms_to(T, Movable)». Откуда взялось требование, которого нет в задаче?">
    От `List`. Чтобы хранить элементы, он должен уметь их перемещать,
    и это требование передаётся вашему параметру. Задача про цены здесь
    ни при чём — надо дописать `& Movable`. Та же ситуация разбиралась
    в главе [Параметризация](/meta/parameters/).
  </QuizItem>
  <QuizItem q="У вас есть `List[Book]` и `List[Coffee]`, у обоих типов реализован `price()`. Можно ли сложить их в один список и вызвать `total` один раз?">
    Нет. `List[Priced]` не существует: трейт — это требование к типу,
    а не тип. Компилятор ответит `'List' parameter 'T' has 'Movable'
    type, but value has type 'AnyTrait[Priced]'`. Обобщённая функция
    собирается отдельно под каждый конкретный тип, поэтому списки
    приходится держать раздельно.
  </QuizItem>
  <QuizItem q="Тип реализует метод `read()`, но объявлен как `struct Rogue(Copyable)`. Подойдёт ли он функции `average[T: Sensor]`?">
    Нет. В Mojo нет утиной типизации: соответствие объявляется явно.
    Компилятор скажет `argument type 'Rogue' does not conform to trait
    'Sensor'`, и лечится это дописыванием трейта в скобки.
  </QuizItem>
  <QuizItem q="Трейт `Sensor` даёт реализацию `label` по умолчанию, и в вашей структуре тоже написан `label`. Какой вызовется? А если второй трейт тоже даёт `label`?">
    Вызовется ваш: реализация в структуре всегда важнее той, что в трейте.
    А вот два трейта с одинаковым методом — уже конфликт, и компилятор
    откажется выбирать: `conflicting default implementations in 'A' and
    'B'; you must implement it manually`. Значит, придётся написать метод
    в структуре явно.
  </QuizItem>
  <QuizItem q="Вы делаете свой тип ключом словаря и объявили `Hashable`. Хватит ли этого?">
    Нет. `Dict` требует `KeyElement`, а это, по словам самого
    компилятора, `Equatable & Hashable & Movable`. Без сравнения
    на равенство словарь не отличит совпадение хешей от совпадения
    ключей.
  </QuizItem>
</Quiz>
