Самая коварная ошибка при работе с памятью — ссылка, которая пережила то,
на что указывала. В C она называется висячим указателем и приводит к чтению
чужих данных. В Python её просто не бывает: пока на объект есть обычная ссылка,
он жив.

Mojo идёт третьим путём: сборщика мусора нет, но компилятор **доказывает**,
что ссылка не переживёт своё значение. Инструмент для этого доказательства
называется **origin** — происхождение.

## Что такое origin

Origin — это ярлык «откуда взялась ссылка». Не тип, не значение, а пометка
на этапе компиляции: вот эта ссылка происходит из вон той переменной.

Зная происхождение, компилятор понимает, как долго ссылка имеет право жить:
ровно столько, сколько живёт её источник. Дальше он просто сверяет ярлыки —
никакой работы во время выполнения программы здесь не происходит.

Вы уже видели origin в главе про конвенции:

```mojo
def longer(ref a: String, ref b: String) -> ref [a, b] String:
    return a if a.byte_length() > b.byte_length() else b
```

В квадратных скобках после `ref` — список источников. Здесь: «результат
происходит либо из `a`, либо из `b`».

## В скобках пишут место, а не контейнер

Вот главная тонкость, на которой спотыкаются все. Попробуем вернуть ссылку
на поле структуры:

```mojo
def balance_ref(ref self) -> ref [self] Int:
    return self.balance      # ошибка
```

<CompilerError msg="error: cannot return reference with incompatible origin: 'origin_of(self.balance)' vs 'origin_of(self)'">
  <Fragment slot="meaning">
    Вы обещали ссылку с происхождением «структура целиком», а вернули
    ссылку на её поле. Для компилятора это разные происхождения:
    у поля своё, у структуры своё.
  </Fragment>
  <Fragment slot="fix">
    Назовите в скобках то самое место, откуда берёте ссылку:

    ```mojo
    def balance_ref(ref self) -> ref [self.balance] Int:
        return self.balance
    ```
  </Fragment>
</CompilerError>

Правило простое: **что возвращаете — то и указывайте в скобках**.

## Ссылка на элемент коллекции

Тот же приём решает задачу, которую мы дважды откладывали. Наивная попытка:

```mojo
def biggest(ref numbers: List[Int]) -> ref [numbers] Int:
    return numbers[0]        # ошибка
```

```text
error: cannot return reference with incompatible origin: 'origin_of(numbers["element"])' vs 'origin_of(numbers)'
```

Компилятор говорит прямым текстом: у элемента происхождение
`numbers["element"]`, а вы назвали `numbers`. Записывается это так же —
местом, откуда берётся ссылка:

```mojo
def biggest(ref numbers: List[Int]) -> ref [numbers[0]] Int:
    var best = 0
    for index in range(len(numbers)):
        if numbers[index] > numbers[best]:
            best = index
    return numbers[best]


def main():
    var scores: List[Int] = [3, 9, 4]
    print(biggest(scores))
    biggest(scores) = 0
    print(scores[0], scores[1], scores[2])
```

<Result output={"9\n3 0 4"} />

Индекс в скобках — не «нулевой элемент», а способ сказать «элемент этого
списка». Возвращать можно любой: в примере вернулся элемент с индексом 1,
и запись через результат обнулила именно его.

Насколько это чистый маркер, видно из простого опыта: `ref [numbers[999]]`
для списка из трёх элементов компилируется и работает. Индекс в скобках
вообще не вычисляется — компилятор читает из него только «элемент вот этого
списка».

<Aside type="note" title="Почему нельзя написать `origin_of(numbers[«element»])`">
  В тексте ошибки происхождение выглядит как `numbers["element"]`, и рука
  тянется скопировать это в сигнатуру. Не получится: так компилятор
  показывает своё внутреннее устройство, а из пользовательского кода
  подписаться на «элемент» строкой нельзя — попытка даёт
  `error: no matching method in call to '__getitem__'`.

  Пишите обычное выражение доступа: `numbers[0]`.
</Aside>

## Как компилятор ловит висячую ссылку

Теперь самое интересное. Возьмём ссылку на элемент, изменим список
и попробуем ей воспользоваться:

```mojo
var xs: List[Int] = [1, 2, 3]
var p = Pointer(to=xs[0])
xs.append(4)
print(p[])            # ошибка
```

<CompilerError msg="error: use of invalidated interior reference 'xs[&quot;element&quot;]'">
  <Fragment slot="meaning">
    `append` может перевыделить память под список, и все ссылки внутрь него
    перестают быть действительными. Компилятор это знает и указывает
    на строку, где всё сломалось:

    ```text
    note: origin was invalidated here
        xs.append(4)
    ```
  </Fragment>
  <Fragment slot="fix">
    Либо возьмите ссылку заново после изменения списка, либо запомните
    не ссылку, а индекс — он переживёт перевыделение.
  </Fragment>
</CompilerError>

Проверено, что происхождение рушат `append`, `insert`, `pop`, `clear`
и `resize` — всё, что может подвинуть данные. А вот чтение и запись
по другому индексу ссылку не ломают: `xs[1] = 42` при живой ссылке
на `xs[0]` компилируется.

Работает это и через границу функции. Если список меняет вызванная
функция, компилятор всё равно поймает — и покажет строку вызова:

```text
note: origin was invalidated here
    grow(xs)
```

Это тот самый класс ошибок, который в C++ называется *iterator
invalidation*: изменили вектор во время обхода — и получили неопределённое
поведение, которое проявится когда-нибудь потом и не там. Если ссылку
вы держите явно, здесь программа просто не соберётся.

<PyMojo>
  <Fragment slot="python">
```python
xs = [1, 2, 3]
it = iter(xs)
xs.append(4)
# RuntimeError только у dict и set,
# у списка — молча странное поведение
```
  </Fragment>
  <Fragment slot="mojo">
```mojo
var xs: List[Int] = [1, 2, 3]
var p = Pointer(to=xs[0])
xs.append(4)
print(p[])   # не компилируется
```
  </Fragment>
  <Fragment slot="note">
    Python ловит изменение во время обхода только у словарей и множеств,
    и делает это во время выполнения. У списка он не ругается, но и памяти
    не портит: итератор просто хранит индекс, и вы получаете сюрприз
    в логике. Mojo ловит обращение к устаревшей ссылке до запуска — а вот
    если поймать не удалось, сюрприз будет уже в памяти. Об этом ниже.
  </Fragment>
</PyMojo>

### Ловится использование, а не сам факт

Важная деталь, которая экономит нервы: компилятор ругается не на то, что
вы изменили список при живой ссылке, а на **обращение к ссылке после
изменения**. Если ссылка больше не нужна — всё в порядке:

```mojo
def main():
    var queue: List[Int] = [1, 2]
    var head = Pointer(to=queue[0])
    print(head[])
    queue.append(3)
    print(len(queue))
```

<Result output={"1\n3"} />

Здесь последнее использование `head` — до `append`, и никакого конфликта
нет. Это то же правило «до последнего использования», что и у владения:
ссылка живёт ровно столько, сколько нужна.

## Владельца нельзя увезти из-под ссылки

Origin работает и в другую сторону: пока ссылка нужна, значение нельзя
передать другому владельцу.

```mojo
var s = String("привет")
var p = Pointer(to=s)
var moved = s^
print(p[])            # ошибка: use of uninitialized value 's'
```

Компилятор видит, что `p` ещё понадобится, и не даёт увезти `s`.

<Aside type="danger" title="Чего Mojo 1.0 не ловит — и чем это грозит">
  Защита не абсолютная. Изменение списка внутри обычного цикла
  **компилируется**: ссылку здесь держит итератор внутри себя, и компилятор
  её не видит.

  ```mojo
  for value in xs:
      if value == 1:
          xs.append(99)
      print("v:", value)
  ```

  Но «компилируется» тут не значит «работает». Это неопределённое
  поведение: итератор хранит указатель на буфер, а `append` может этот
  буфер перевыделить. Что получится — зависит от запаса ёмкости:

  - для `List[Int]` из примера выше выводится `v: 0`, `v: 2`, `v: 3` —
    первый элемент прочитан из освобождённой памяти;
  - для `List[String]` с несколькими `append` программа падает:
    `error: execution crashed`;
  - иногда всё проходит гладко — и это худший вариант, потому что ошибка
    затаится до другого размера данных.

  Даже когда не падает, поведение отличается от питоновского: новые
  элементы обход не увидит, потому что итератор запомнил длину заранее.

  Вывод: привычку не менять коллекцию во время обхода стоит не просто
  сохранить — здесь цена ошибки выше, чем в Python. Меняете список во время
  обхода — собирайте изменения в отдельный список и применяйте после цикла.
</Aside>

## Указатель — это ссылка, которую можно положить в переменную

`ref` живёт в сигнатурах функций. Если ссылка нужна как обычное значение,
берут `Pointer`:

```mojo
def main():
    var total = 10
    var pointer = Pointer(to=total)
    pointer[] += 5
    print(total)
```

<Result output={"15"} />

Разыменование — квадратные скобки без индекса: `pointer[]`. Origin
у `Pointer` тоже есть, он просто спрятан в типе, поэтому все проверки
из этой главы работают и для него.

<Aside type="tip" title="Это не тот указатель, которого вы боитесь">
  `Pointer` безопасен: пока вы не попросили обратного явно, он указывает
  на живое значение — за этим следит компилятор. Небезопасный вариант
  в языке тоже есть, он называется `UnsafePointer`, применяется при работе
  с чужой памятью и разбирается в разделе
  [Производительность](/performance/pointers/).
</Aside>

## Ссылку на локальную переменную не вернуть

```mojo
def broken() -> ref [ ... ] String:   # писать в скобках нечего
    var local = String("исчезнет")
    return local
```

Локальная переменная умрёт при выходе из функции, и любой ярлык
происхождения оказался бы враньём. В любом безопасном коде компилятор
это заметит:

```text
error: cannot return reference with incompatible origin: 'origin_of(local)' vs ...
```

Возвращайте значение, а не ссылку на него, — как раз для этого владение
и передаётся.

<Quiz>
  <QuizItem q="Что пишут в квадратных скобках после `ref` в типе возврата?">
    Место, откуда берётся ссылка: `ref [self.balance]` для поля структуры,
    `ref [numbers[0]]` для элемента списка, `ref [a, b]` если источников
    несколько. Указать контейнер вместо самого места — частая ошибка:
    у поля и у элемента происхождение своё.
  </QuizItem>
  <QuizItem q="Почему `ref [numbers] Int` не годится для возврата элемента списка?">
    Потому что у элемента другое происхождение, чем у самого списка.
    Компилятор так и говорит: `origin_of(numbers["element"])` вместо
    `origin_of(numbers)`. Правильная запись — `ref [numbers[0]]`, где
    индекс просто указывает на элемент этого списка, любой.
  </QuizItem>
  <QuizItem q="Что произойдёт, если сохранить ссылку на элемент и вызвать `append`?">
    Программа не соберётся: `use of invalidated interior reference`,
    и компилятор покажет строку, где происхождение стало недействительным.
    Но только если ссылкой пользуются ПОСЛЕ изменения — если её последнее
    использование раньше, всё в порядке.
  </QuizItem>
  <QuizItem q="Можно ли вернуть ссылку на локальную переменную функции?">
    Нет. Локальная переменная умрёт при выходе, и назвать её как источник
    ссылки нечем. Возвращайте само значение — передача владения для этого
    и существует.
  </QuizItem>
</Quiz>
