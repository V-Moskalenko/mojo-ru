В Python исключение может прилететь из любой строки: вы никогда не знаете
заранее, бросит функция ошибку или нет, пока не прочитаете её код целиком
вместе со всем, что она вызывает.

В Mojo способность бросать исключение — **часть сигнатуры**. Компилятор
следит за этим так же строго, как за типами.

## `raises` — обещание в сигнатуре

Функция, которая может бросить исключение, обязана это объявить:

```mojo
def parse(text: String) raises -> Int:
    return Int(text)
```

Слово `raises` ставится после круглых скобок и перед стрелкой. Забудете —
компилятор не пропустит:

<CompilerError msg="error: 'raise' requires a surrounding 'try' block or the enclosing function to declare 'raises'">
  <Fragment slot="meaning">
    Внутри функции есть `raise`, но в сигнатуре нет `raises`. Обещание
    и поведение разошлись.
  </Fragment>
  <Fragment slot="fix">
    Либо допишите `raises` в сигнатуру и переложите обработку на вызывающий
    код, либо обработайте ошибку прямо здесь, в `try` / `except`.
  </Fragment>
</CompilerError>

<Aside type="caution" title="`raises` теперь пишут явно">
  Раньше в Mojo было два вида функций — `def` и `fn`, и относились они
  к исключениям по-разному. В 1.0 `fn` удалён (`error: 'fn' has been
  removed; use 'def' instead`), остался один `def`, и правило стало
  единым: без `raises` функция бросить не может, и компилятор это
  гарантирует. Если читаете статьи или код, написанные до 1.0, держите
  отличие в голове.
</Aside>

## Вызов тоже под контролем

Обещание работает в обе стороны. Вызвать бросающую функцию из обычной
нельзя:

<CompilerError msg="error: cannot call function that may raise in a context that cannot raise">
  <Fragment slot="meaning">
    Вы вызвали функцию с `raises` из функции без `raises` и без `try`.
    Ошибке некуда деваться.
  </Fragment>
  <Fragment slot="fix">
    Компилятор сам подсказывает два выхода — они же и есть единственные:

    ```text
    note: try surrounding the call in a 'try' block
    note: or mark surrounding function as 'raises'
    ```

    Первое — обработать здесь. Второе — передать ответственность выше.
  </Fragment>
</CompilerError>

Именно поэтому в примерах курса нередко встречается `def main() raises:` —
это верхний этаж, дальше передавать некому.

<PyMojo>
  <Fragment slot="python">
```python
def load(path):        # бросает или нет?
    return open(path).read()
```
  </Fragment>
  <Fragment slot="mojo">
```mojo
def load(path: String) raises -> String:
    ...                # видно из сигнатуры
```
  </Fragment>
  <Fragment slot="note">
    В Python, чтобы узнать это, нужно прочитать тело функции и всё, что
    она вызывает. В Mojo достаточно одной строки сигнатуры — и компилятор
    не даст ей соврать.
  </Fragment>
</PyMojo>

## Тип ошибки ровно один

`raise` принимает значение типа `Error` — или просто строку, которая
в него превратится:

```mojo
def check(age: Int) raises:
    if age < 0:
        raise Error("возраст отрицательный")
    if age > 150:
        raise "возраст слишком большой"


def main():
    try:
        check(-5)
    except e:
        print(e)
```

<Result>
возраст отрицательный
</Result>

Своих классов исключений в Mojo 1.0 нет:

<CompilerError msg="error: cannot implicitly convert 'ParseError' value to 'Error'">
  <Fragment slot="meaning">
    Вы попытались бросить собственную структуру. Иерархии исключений,
    как в Python, в языке пока нет — тип ошибки единственный.
  </Fragment>
  <Fragment slot="fix">
    Различайте ошибки по тексту сообщения либо, если различие важно
    для логики, возвращайте результат через `Optional` или собственный
    тип-результат вместо исключения.
  </Fragment>
</CompilerError>

Практический приём — префикс в сообщении:

```mojo
def check(age: Int) raises:
    if age < 0:
        raise Error("ввод: возраст отрицательный")


def main():
    try:
        check(-5)
    except e:
        if String(e).startswith("ввод:"):
            print("это ошибка пользователя, попросим ввести заново")
        else:
            print("это сбой программы:", e)
```

<Result>
это ошибка пользователя, попросим ввести заново
</Result>

## `try` / `except` / `else` / `finally`

Все четыре блока работают как в Python, но синтаксис `except` короче:

```mojo
def risky(fail: Bool) raises:
    if fail:
        raise Error("плановый сбой")


def main() raises:
    try:
        print("пробуем")
        risky(True)
    except e:
        print("except:", e)
    else:
        print("else: ошибок не было")
    finally:
        print("finally: выполняется всегда")
```

<Result>
пробуем
except: плановый сбой
finally: выполняется всегда
</Result>

- `except e:` — ошибка попадает в переменную `e`;
- `except:` — без переменной, когда текст не нужен;
- `else:` — выполняется, только если исключения не было;
- `finally:` — выполняется в любом случае.

<CompilerError msg="error: expected ':' after 'except'">
  <Fragment slot="meaning">
    Вы написали питоновское `except Error as e:`. В Mojo такой формы нет —
    ловить по типу нечего, тип всегда `Error`.
  </Fragment>
  <Fragment slot="fix">
    Пишите просто `except e:` — переменная указывается сразу, без `as`.
  </Fragment>
</CompilerError>

## Компилятор знает, что может сломаться

Приятный побочный эффект строгости: `try` вокруг кода, который не бросает,
не остаётся незамеченным.

```text
warning: 'except' logic is unreachable, try doesn't raise an exception
```

Это предупреждение стоит воспринимать как подсказку: либо вы обернули
не ту строку, либо `try` здесь лишний. В Python такую ошибку не находит
никто, и мёртвый `except` живёт в коде годами.

## Не всякий сбой — исключение

Важная граница, которую легко не заметить. Выход за границы списка
исключением **не является**:

```mojo
var xs: List[Int] = [1, 2, 3]
print(xs[10])
```

<Result>
At: main.mojo:3:13: Assert Error: index 10 is out of bounds, valid range is 0 to 2
…
mojo: error: execution crashed
</Result>

Программа падает сразу, и `try` / `except` вокруг такой строки не поможет —
более того, компилятор выдаст на него то самое предупреждение
«try doesn't raise an exception».

<Aside type="note" title="Почему так сделано">
  Исключение — это ожидаемая ситуация: файла нет, строка не разбирается,
  сеть недоступна. Выход за границу массива — это **ошибка в коде**,
  и ловить её на ходу бессмысленно: программа уже работает не так,
  как задумано.

  Проверка границ при этом никуда не делась — она есть и включена
  по умолчанию. Просто её результат не исключение, которое можно поймать
  и продолжить, а немедленная остановка: чинить нужно код, а не последствия.
</Aside>

## Уровни проверок

Свои проверки такого рода пишутся через `debug_assert`. Но есть тонкость,
которую стоит узнать сразу: по умолчанию они **не выполняются**.

```mojo
def main():
    var x = -5
    debug_assert(x > 0, "x должен быть положительным")
    print("после проверки")
```

<Result>
после проверки
</Result>

Условие ложно, а программа спокойно идёт дальше. Это не ошибка, а настройка:
уровень проверок задаётся флагом `-D ASSERT`.

| Значение | Что включено | Когда использовать |
| --- | --- | --- |
| `safe` | проверки стандартной библиотеки: границы списков и подобное | по умолчанию, обычная работа |
| `all` | то же плюс ваши `debug_assert` | отладка и тесты |
| `none` | ничего | замер производительности отлаженного кода |

```bash
uv run mojo -D ASSERT=all main.mojo
```

<Result>
At: main.mojo:3:17: Assert Error: x должен быть положительным
…
mojo: error: execution crashed
</Result>

<Aside type="danger" title="`ASSERT=none` снимает и проверку границ">
  С этим флагом `xs[10]` для списка из трёх элементов уже не падает —
  он читает чужую память и печатает мусор. Проверено: вместо аварийной
  остановки программа спокойно вывела `0`.

  Это ровно то поведение, за которое ругают C: скорость в обмен
  на отсутствие страховки. Включайте `none`, только когда код отлажен
  и вы замеряете производительность.
</Aside>

## `Optional` — когда ошибка не нужна

Часто «значения нет» — это не ошибка, а обычный исход. Для таких случаев
есть `Optional`, доступный без импорта:

```mojo
def main():
    var found = Optional[Int](42)
    var missing = Optional[Int]()

    if found:
        print("есть значение:", found.value())
    if not missing:
        print("значения нет")

    print(missing.or_else(0))
```

<Result>
есть значение: 42
значения нет
0
</Result>

Стандартная библиотека и сама этим пользуется — например, `Dict.get()`
не бросает исключение, а возвращает `Optional`:

```mojo
def main():
    var codes = Dict[String, Int]()
    codes["Москва"] = 495

    print(Bool(codes.get("Казань")))
    print(codes.get("Москва", 0))
```

<Result>
False
495
</Result>

Сравните с обращением по ключу `codes["Казань"]` — оно бросает исключение
и требует `raises`. Оба варианта в языке есть, и выбирать вам.

### Что выбрать

| Ситуация | Инструмент |
| --- | --- |
| Значения может не быть — это нормально | `Optional` |
| Что-то пошло не так, и вызывающий код должен узнать причину | `raise` |
| Ошибка в самом коде, программа дальше бессмысленна | `debug_assert` |

Правило простое: если по итогам нужно **объяснение**, бросайте исключение.
Если достаточно ответа «нет» — берите `Optional`, он дешевле и не заражает
`raises` всю цепочку вызовов.

## Контекстные менеджеры

`with` работает как в Python: нужен тип с методами `__enter__` и `__exit__`.

```mojo
@fieldwise_init
struct Section(ImplicitlyCopyable):
    var title: String

    def __enter__(self) -> Self:
        print("--", self.title)
        return self

    def __exit__(self):
        print("-- конец:", self.title)


def main():
    try:
        with Section("замер"):
            print("работаем")
            raise Error("сбой внутри with")
    except e:
        print("поймали:", e)
```

<Result>
-- замер
работаем
-- конец: замер
поймали: сбой внутри with
</Result>

Обратите внимание на порядок: `__exit__` вызвался **до** того, как ошибка
дошла до `except`. Ради этого `with` и существует — что бы ни случилось
внутри блока, файл закроется, замок освободится, замер завершится.

## Если ошибку никто не поймал

Программа завершается с ненулевым кодом и печатает две строки — сначала
подсказку, потом само сообщение:

```text
stack trace was not collected. Enable stack trace collection with environment variable `MODULAR_DEBUG=stack-trace-on-error`
Unhandled exception caught during execution: String is not convertible to integer with base 10: 'не число'
```

Подсказка честная, но с оговорками. Стек действительно собирается, если
задать переменную:

```bash
MODULAR_DEBUG=stack-trace-on-error uv run mojo main.mojo
```

Только в таком виде это будут голые адреса без имён функций. Читаемый стек
с именами и номерами строк даёт лишь отдельно собранный бинарник
с отладочной информацией:

```bash
uv run mojo build -debug-level=full main.mojo
MODULAR_DEBUG=stack-trace-on-error ./main
```

<Aside type="note" title="Не для всякой ошибки">
  Для исключений, рождающихся внутри стандартной библиотеки — например,
  из `Int(String("не число"))`, — стек не собирается даже с этой
  переменной: Mojo так и напишет `stack trace was not collected`.
  Собирается он для ошибок, поднятых вашим собственным `raise`.
</Aside>

<Quiz>
  <QuizItem q="Чем `raises` в Mojo отличается от исключений в Python?">
    В Python бросить исключение может любая функция, и узнать об этом
    можно только прочитав её код. В Mojo способность бросать исключение —
    часть сигнатуры: функция объявляет `raises`, а вызывающий код обязан
    либо обернуть вызов в `try`, либо тоже объявить `raises`.
  </QuizItem>
  <QuizItem q="Можно ли поймать выход за границы списка через try/except?">
    Нет. `xs[10]` для списка из трёх элементов — это `Assert Error`,
    программа падает сразу. Исключения предназначены для ожидаемых
    ситуаций, а выход за границу — ошибка в коде. Компилятор даже
    предупредит, что `except` вокруг такой строки недостижим.
  </QuizItem>
  <QuizItem q="Когда лучше вернуть `Optional`, а когда бросить исключение?">
    Если «значения нет» — нормальный исход и объяснять нечего, берите
    `Optional`: он не заставляет всю цепочку вызовов объявлять `raises`.
    Если нужно передать причину сбоя — бросайте исключение.
  </QuizItem>
  <QuizItem q="Как объявить собственный тип исключения?">
    Никак: в Mojo 1.0 тип ошибки единственный — `Error`. Различают ошибки
    по тексту сообщения (например, по префиксу) либо возвращают результат
    другим способом — через `Optional` или свой тип-результат.
  </QuizItem>
</Quiz>
