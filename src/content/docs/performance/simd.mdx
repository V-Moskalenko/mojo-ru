Процессор умеет складывать не два числа, а два **набора** чисел — одной
командой. Шестнадцать сложений за то же время, что одно. Это называется
SIMD: *single instruction, multiple data*, одна команда над многими
данными.

В Python эта возможность спрятана внутри NumPy, и добраться до неё
из своего кода нельзя. В Mojo она — обычный тип языка.

## Тип `SIMD`

```mojo
def main():
    var v = SIMD[DType.float32, 4](1.0, 2.0, 3.0, 4.0)
    var w = SIMD[DType.float32, 4](10.0)

    print("вектор:", v)
    print("сумма:", v + w)
    print("произведение:", v * w)
    print("reduce_add:", v.reduce_add())
    print("элемент:", v[2])
```

<Result output={"вектор: [1.0, 2.0, 3.0, 4.0]\nсумма: [11.0, 12.0, 13.0, 14.0]\nпроизведение: [10.0, 20.0, 30.0, 40.0]\nreduce_add: 10.0\nэлемент: 3.0"} />

Два параметра: **тип элемента** и **сколько их**. Оба известны при сборке
— иначе процессор не знал бы, какую команду выполнять.

Обратите внимание на `SIMD[DType.float32, 4](10.0)`: одно число
размножилось по всем полосам. Это частый приём — умножить весь вектор
на скаляр.

<Aside type="tip" title="`Float64` — тоже SIMD">
  `Float64` — это `SIMD[DType.float64, 1]`, вектор из одного элемента.
  Присваивание между ними работает напрямую:

  ```mojo
  var a: SIMD[DType.float64, 1] = 2.5
  var b: Float64 = a          # то же самое
  ```

  Отсюда и `Scalar[DType.float32]` — просто имя для вектора ширины 1.
  Поэтому арифметика над числами и над векторами выглядит одинаково:
  это буквально один и тот же код.

  А вот `Int` в этот ряд **не входит** — это отдельный тип машинного
  слова, и неявно он не превращается ни во что:

  ```text
  error: cannot implicitly convert 'Int64' value to 'Int'
  ```

  Так что «в Mojo нет скалярных типов» — красивая фраза, но неверная.
</Aside>

## Какая ширина у вашей машины

Жёстко зашивать четвёрку не стоит: на одном процессоре за раз проходит
четыре числа, на другом шестнадцать. Правильную ширину подскажет
компилятор:

```mojo
from std.sys import simd_width_of


def main():
    print("float32:", simd_width_of[DType.float32]())
    print("float64:", simd_width_of[DType.float64]())
    print("int8:   ", simd_width_of[DType.int8]())
```

На машине, где писалась эта глава:

```text
float32: 16
float64: 8
int8:    64
```

Шестнадцать чисел `float32` — это 512 бит, то есть процессор
с AVX-512. У вас, скорее всего, будет 8 или 4 — и это нормально.

Обратите внимание на закономерность: чем меньше элемент, тем больше
их помещается. Регистр один и тот же, меняется только нарезка.

<Aside type="caution" title="Имя функции поменялось в 1.0">
  До 1.0 она называлась `simdwidthof` — одним словом, — и именно так
  написано во всех старых статьях и примерах. Компилятор 1.0.0 такого
  имени не знает и ничем не помогает:

  ```text
  error: use of unknown declaration 'simdwidthof'
  ```

  Попытка импортировать старое имя тоже ни к чему не приведёт:

  ```text
  error: package 'sys' does not contain 'simdwidthof'
  ```

  А вот **новое** имя, забытое в импорте, компилятор подскажет сам —
  запомнить путь не придётся:

  ```text
  error: use of unknown declaration 'simd_width_of'; did you mean to import it from 'std.sys'? Add 'from std.sys import simd_width_of'
  ```
</Aside>

## Чтение и запись памяти вектором

Из списка данные в вектор кладут не по одному, а сразу пачкой:

```mojo
from std.sys import simd_width_of


def main():
    var data = List[Float32](capacity=20)
    for i in range(20):
        data.append(Float32(i))

    var ptr = data.unsafe_ptr()

    var chunk = ptr.unsafe_load[width=4](0)
    print("загружено:", chunk)

    ptr.unsafe_store(0, chunk * 2.0)
    print("после записи:", data[0], data[1], data[2], data[3])
```

<Result output={"загружено: [0.0, 1.0, 2.0, 3.0]\nпосле записи: 0.0 2.0 4.0 6.0"} />

Слово `unsafe` в названии честное: границы никто не проверяет. Загрузить
шестнадцать чисел, начиная с предпоследнего, вам никто не помешает —
и прочитается чужая память.

<Aside type="caution" title="`load` и `store` устарели">
  Раньше методы назывались просто `load` и `store`. Они ещё работают,
  но компилятор просит переименовать:

  ```text
  warning: 'load' is deprecated, use 'unsafe_load' instead
  warning: 'store' is deprecated, use 'unsafe_store' instead
  ```

  Новые имена лучше: они не дают забыть, что проверок нет.
</Aside>

## Хвост

Массивы редко бывают кратны ширине вектора. Тысяча элементов при ширине
шестнадцать — это 62 полных вектора и 8 штук в остатке, которые придётся
досчитать по одному:

```mojo
var full = (len(data) // W) * W

for i in range(0, full, W):        # основная часть — вектором
    accumulator += ptr.unsafe_load[width=W](i)

var total = accumulator.reduce_add()

for i in range(full, len(data)):   # хвост — поштучно
    total += data[i]
```

Забыть про хвост — самая частая ошибка в векторном коде: результат
получается почти правильным, и на маленьких тестах расхождение легко
не заметить.

## Редукция: из вектора обратно в число

Аккумулятор в примере выше — не число, а вектор из `W` независимых
накопителей. Каждый складывал свою полосу. Собрать их в одно значение
можно методами `reduce_*`:

| Метод | Что делает |
| --- | --- |
| `reduce_add()` | сумма всех полос |
| `reduce_max()` / `reduce_min()` | наибольшее / наименьшее |
| `reduce_mul()` | произведение |

<Aside type="caution" title="Сравнение вектора — не оператором">
  Написать `v > 2.0` для вектора нельзя, и компилятор объясняет почему:

  ```text
  note: constraint failed: Strict inequality is only defined for `Scalar`s; did you mean to use `SIMD.gt(...)`?
  ```

  Оператор `>` обязан вернуть один `Bool` — а поэлементное сравнение
  даёт вектор из `Bool`. Поэтому для вектора зовут метод:

  ```mojo
  v.gt(2.0)     # [False, False, True, True]
  ```
</Aside>

## Сколько это даёт на самом деле

Сумма массива из 8192 чисел `float32`, замер по методике из главы
[Как честно мерить скорость](/performance/benchmarking/) — минимум
из партий, данные в куче, контрольная сумма сходится:

| Способ | Наносекунд на элемент |
| --- | --- |
| поэлементно | 1,254 |
| вектором (ширина 16) | 0,073 |

Примерно **в семнадцать раз**. Восемь прогонов дали от 15,7 до 17,5 —
то есть ускорение колеблется вокруг шестнадцати, ровно как и обещает
ширина вектора. Отклонения в обе стороны — шум измерения, объяснять
их нечем.

### Ширина — не единственный резерв

Здесь легко остановиться, решив, что потолок достигнут. Это не так,
и проверяется просто: добавим **независимые накопители**, чтобы соседние
сложения не ждали друг друга.

| Версия | Наносекунд на элемент |
| --- | --- |
| поэлементно, один накопитель | 1,254 |
| поэлементно, четыре накопителя | 0,303 |
| вектором, один накопитель | 0,073 |
| вектором, четыре накопителя | 0,026 |

Оба столбца ускорились примерно вчетверо и втрое. Значит, **обе** версии
упирались не только в количество данных за такт, но и в длину цепочки:
каждое сложение ждало результата предыдущего.

<Aside type="note" title="Что здесь на самом деле происходит">
  Сложение с плавающей точкой занимает несколько тактов. Пока результат
  не готов, следующее сложение начать нельзя — если оно к тому же
  накопителю. Получается очередь длиной во весь массив.

  Вектор укорачивает эту очередь в шестнадцать раз (8192 сложения
  превращаются в 512), но не убирает. Четыре независимых накопителя
  укорачивают её ещё вчетверо — и процессор наконец загружен.

  Итог: **48,8 раза** относительно наивного цикла. Из них шестнадцать —
  ширина вектора, остальное — исчезнувшее ожидание.
</Aside>

Именно поэтому библиотечная векторизация из следующей главы не просто
режет массив на векторы, но ещё и разворачивает цикл.

<Aside type="danger" title="Векторная сумма даёт другой ответ">
  Сложение чисел с плавающей точкой **не ассоциативно**: `(a + b) + c`
  и `a + (b + c)` могут отличаться. Векторная редукция складывает
  в другом порядке — значит, и результат другой.

  Проверено на массиве из 4096 элементов: одно число `1.0e8` и 4095
  единиц. На ширине 16:

  ```text
  скаляр: 100000000.0
  вектор: 100003840.0
  ```

  Точный ответ — 100004095. Поэлементная сумма потеряла **все** единицы:
  к стомиллионному значению единица в `float32` просто не добавляется.
  Векторная разложила слагаемые по шестнадцати полосам: пятнадцать
  из них накапливали только единицы и ничего не потеряли, и лишь одна —
  та, куда попало большое число, — потеряла свои 255. Отсюда и ошибка
  ровно в 255 вместо 4095.

  На другой ширине и число будет другим: при восьми полосах выходит
  100003580, при четырёх — 100003070.

  Вывод не «SIMD точнее», а «результат другой». Если ваш код сверяется
  с эталоном до последнего бита — векторизация его сломает, и это
  придётся учесть.
</Aside>

Программа печатает не ширину вектора и не время: и то и другое у вас
будет своё. Печатает она то, что от машины не зависит, — совпадение
результатов.

<Aside type="tip" title="Проверяйте векторный код контрольной суммой">
  Первое, что стоит написать рядом с векторной версией, — простая
  поэлементная, и сравнить результаты. Она медленная, зато очевидно
  правильная.

  Так ловятся обе главные ошибки: забытый хвост и перепутанные индексы.
  А если результаты разошлись в последних знаках — вы наткнулись
  на неассоциативность, и это тоже полезно знать заранее.
</Aside>

<Quiz>
  <QuizItem q="Почему у `SIMD` оба параметра — тип элемента и ширина — должны быть известны при сборке?">
    Потому что от них зависит, какую машинную команду выпустит
    компилятор. Сложение восьми `float32` и восьми `float64` — разные
    команды над разными регистрами. Ширина времени выполнения означала бы,
    что команду надо выбирать при каждом вызове, а это уже не SIMD.
  </QuizItem>
  <QuizItem q="Что не так с `SIMD[DType.float32, 8]`, зашитым в код руками?">
    Восьмёрка верна не везде. На процессоре с AVX-512 за раз проходит
    шестнадцать чисел `float32`, и половина возможностей пропадёт;
    на более старом — вектор придётся эмулировать. Правильно спросить
    у компилятора: `simd_width_of[DType.float32]()`.
  </QuizItem>
  <QuizItem q="Массив из 1000 чисел, ширина вектора 16. Что произойдёт, если написать только `for i in range(0, len(data), 16)`?">
    Цикл зайдёт за границу массива: на 63-м шаге `i` станет 992,
    и загрузка шестнадцати чисел прочитает 8 элементов чужой памяти —
    проверок у `unsafe_load` нет. Нужно считать до `(len // 16) * 16`,
    а оставшиеся 8 элементов досчитать по одному.
  </QuizItem>
  <QuizItem q="Векторная сумма массива float дала не то же число, что поэлементная. Это ошибка?">
    Нет, это свойство арифметики с плавающей точкой: сложение
    не ассоциативно, а редукция складывает в другом порядке. Причём
    векторная версия нередко **точнее**: каждая полоса накапливает свою
    часть и не теряет малые слагаемые. Но если результат должен совпадать
    с эталоном побитово — векторизовать нельзя.
  </QuizItem>
  <QuizItem q="Векторная версия дала 17× при ширине 16. Значит, потолок достигнут?">
    Нет. Проверяется добавлением независимых накопителей: векторная
    версия с четырьмя накопителями вместо одного ускоряется ещё почти
    втрое — 0,073 против 0,026 нс на элемент, итого 48,8× к наивному
    циклу. Значит, вектор снял ограничение по данным за такт,
    но осталось второе — цепочка сложений, где каждое ждёт предыдущего.
    А сами 17 вместо 16 — просто шум: прогоны давали от 15,7 до 17,5.
  </QuizItem>
</Quiz>
