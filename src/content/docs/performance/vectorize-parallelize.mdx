В прошлой главе мы резали массив на векторы руками: считали, сколько
влезло полных, и досчитывали хвост по одному. Это ровно тот код, который
не хочется писать дважды.

Библиотека умеет делать это сама — и заодно закрывает второй резерв,
который мы там намерили.

## `vectorize`

```mojo
from std.algorithm import vectorize
from std.sys import simd_width_of

comptime W = simd_width_of[DType.float32]()


def main():
    def step[width: Int](idx: Int):
        print(idx, width)

    vectorize[W](40, step)
```

Сорок элементов при ширине 16. Смотрите, что печатается:

```text
0 16
16 16
32 1
33 1
34 1
...
39 1
```

Два полных вектора, а потом восемь вызовов с шириной **1** — это и есть
хвост. `vectorize` не пишет для него отдельный цикл, а вызывает вашу же
функцию с другой шириной. Поэтому она и объявлена как `step[width: Int]`:
ширина приходит параметром, и один и тот же код обслуживает оба случая.

## Списки захвата

Функция выше ничего не трогала снаружи. Как только понадобятся данные,
всплывёт то, чего в Mojo до 1.0 не было:

<CompilerError msg="error: Could not infer capture convention of the captured value ptr">
  <Fragment slot="meaning">
    Вложенная функция обратилась к переменной из внешней области, а как
    именно её захватывать — по ссылке, по значению, с правом изменять
    или нет — компилятор угадывать не берётся.
  </Fragment>
  <Fragment slot="fix">
    Написать **список захвата** — в фигурных скобках после аргументов:

    ```mojo
    def step[width: Int](idx: Int) {imm ptr}:
        ...
    ```
  </Fragment>
</CompilerError>

Конвенций пять, и они те же, что у аргументов функций:

| Запись | Что значит |
| --- | --- |
| `{imm x}` | ссылка только для чтения |
| `{mut x}` | ссылка с правом изменять |
| `{var x}` | копия, снятая в момент объявления |
| `{var x^}` | значение переезжает внутрь, снаружи больше недоступно |
| `{ref x}` | изменяемость определит вызывающий |

Имя можно не писать: `{imm}` захватит всё используемое по неизменяемой
ссылке, `{}` — не захватит ничего.

<Aside type="caution" title="`@parameter` ломает `vectorize`">
  Соблазн пометить вложенную функцию декоратором `@parameter` велик —
  именно так написано во всех примерах до 1.0. Не делайте этого:
  декоратор делает замыкание захватывающим в другом смысле, и
  `vectorize` его не примет.

  ```text
  error: no matching function in call to 'vectorize'
  note: candidate not viable: value passed to 'closure' cannot be converted from 'def[width: Int](idx: Int) capturing thin -> None' to 'func'
  ```

  Причём ошибка появится, даже если функция ничего не захватывает.
  Правильно — обычная вложенная `def` со списком захвата.
</Aside>

## `unroll_factor`: второй резерв

В прошлой главе мы измерили, что после векторизации остаётся ещё почти
трёхкратный запас: цепочка сложений, где каждое ждёт предыдущего.
Разворачивать цикл руками не нужно — у `vectorize` есть параметр:

```mojo
vectorize[W, unroll_factor=4](len(data), step)
```

Библиотека выпустит четыре независимые цепочки вместо одной. Это ровно
тот приём, который в прошлой главе дал 0,073 → 0,026 наносекунды
на элемент.

## Многопоточность: `parallelize`

Здесь читателя ждёт сюрприз, и лучше узнать о нём отсюда.

<Aside type="danger" title="`parallelize` нет в стандартной библиотеке">
  Официальное руководство показывает `parallelize` в примерах, и почти
  все статьи о Mojo берут его из `algorithm`. В Mojo 1.0.0 такого имени
  в стандартной библиотеке **нет** — ни в `std.algorithm`, ни где-либо
  ещё:

  ```text
  error: package 'algorithm' does not contain 'parallelize'
  ```

  Функция переехала в отдельный пакет `max`. Ставится он рядом:

  ```bash
  uv add max
  ```

  После этого работает импорт `from max.algorithm import parallelize`.
  Проверено на 1.0.0 — других путей не нашлось.
</Aside>

Сама функция проста: даёт номер куска, а вы решаете, что с ним делать.

```mojo
from max.algorithm import parallelize


def main():
    var results = List[Int](length=8, fill=0)
    var ptr = results.unsafe_ptr()

    def work(i: Int) {imm ptr}:
        ptr.unsafe_store(i, i * i)

    parallelize(work, 8)

    for i in range(8):
        print(results[i], end=" ")
    print()
```

<Result output={"0 1 4 9 16 25 36 49 "} />

Сколько ядер доступно, подскажет `num_physical_cores()` из `std.sys`.

## Сколько стоит запустить поток

А вот это — главное, ради чего стоит читать раздел. Одна и та же задача
(корень из каждого элемента, запись в другой массив), разбитая на два
куска, на машине с двумя ядрами:

| Элементов | Ускорение от двух потоков |
| --- | --- |
| 256 | **0,035** — в 28 раз медленнее |
| 4 096 | **0,27** — вчетверо медленнее |
| 16 384 | 0,83 — всё ещё медленнее |
| 32 768 | 1,12 |
| 65 536 | 1,54 |

До тридцати тысяч элементов многопоточность не окупается вовсе,
а на маленьких массивах проигрывает катастрофически: запустить поток
дороже, чем посчитать всё в одиночку.

<Aside type="note" title="Почему 1,54, а не 2">
  Даже там, где параллелизм выигрывает, до двукратного ускорения
  на двух ядрах дело не доходит. Причин две: запуск и синхронизация
  потоков стоят времени, а задача упирается в память — два ядра тянут
  данные через одну и ту же шину.

  Правило: **ускорение никогда не равно числу ядер**, и чем легче работа
  над элементом, тем дальше от него результат.
</Aside>

<Aside type="danger" title="Эти числа — не ваши">
  Замер сделан на **двух** физических ядрах (Intel Xeon 2,8 ГГц,
  облачный контейнер). Если у вас восемь или шестнадцать, ни одна цифра
  из таблицы вам не подойдёт, и подобрать её умножением не получится:

  - **потолок** поднимется — но не до числа ядер, а до чего-то заметно
    меньшего, потому что упор в память никуда не денется;
  - **точка окупаемости сдвинется вверх**: чем больше потоков, тем
    дороже их запустить, и тем крупнее должна быть задача, чтобы это
    окупилось.

  Проверить это на восьми ядрах у нас не было возможности, поэтому мы
  и не приводим для них чисел — вместо того чтобы их выдумать.
  Из таблицы стоит запомнить не значения, а **форму**: сначала глубокий
  проигрыш, потом медленный выход в плюс.

  Свои числа — только замером, как в главе
  [Как честно мерить скорость](/performance/benchmarking/).
</Aside>

## Порядок действий

Если код тормозит, браться за инструменты стоит в этом порядке:

1. **Замерить.** Без этого всё остальное — гадание.
2. **Векторизовать** — `vectorize`. Даёт кратно ширине вектора,
   работает всегда, ничего не стоит.
3. **Развернуть** — `unroll_factor`. Ещё в два-три раза, тоже даром.
4. **Распараллелить** — `parallelize`. Только если данных много
   и работа над каждым элементом не пустячная.
5. **Замерить снова.** Особенно после четвёртого пункта.

Первые три шага почти безопасны. Четвёртый — единственный, который может
сделать хуже, и на маленьких данных делает это уверенно.

<Quiz>
  <QuizItem q="Почему функция для `vectorize` объявлена как `step[width: Int](idx: Int)`, а не просто `step(idx: Int)`?">
    Потому что `vectorize` вызывает её с разной шириной: для основной
    части — с полной, а для хвоста — с шириной 1, по одному элементу.
    Один и тот же код обслуживает оба случая, и отдельный цикл для хвоста
    писать не нужно.
  </QuizItem>
  <QuizItem q="Компилятор говорит `Could not infer capture convention of the captured value ptr`. Что это значит?">
    Вложенная функция обратилась к переменной снаружи, а как её
    захватывать — компилятор не угадывает. Нужен список захвата
    в фигурных скобках после аргументов: `{imm ptr}` для чтения,
    `{mut ptr}` если требуется менять.
  </QuizItem>
  <QuizItem q="В старом примере вложенная функция помечена `@parameter`. Можно ли передать её в `vectorize`?">
    Нет. Декоратор делает замыкание `capturing`, а `vectorize` такое
    не принимает — причём ошибка появится, даже если функция ничего
    не захватывает. Нужна обычная вложенная `def` со списком захвата.
  </QuizItem>
  <QuizItem q="Массив из 256 элементов, два ядра. Стоит ли распараллеливать?">
    Категорически нет. На таком размере два потока оказались в 28 раз
    **медленнее** одного: запустить поток дороже, чем выполнить всю
    работу. Окупаться параллелизм начал только после тридцати тысяч
    элементов — и то дав 1,1, а не 2. На машине с большим числом ядер
    порог будет ещё выше: потоков больше, запускать их дороже.
  </QuizItem>
  <QuizItem q="Статья предлагает `from algorithm import parallelize`. Почему не собирается?">
    Потому что в Mojo 1.0 этой функции в стандартной библиотеке нет:
    `package 'algorithm' does not contain 'parallelize'`. Она переехала
    в отдельный пакет `max` — нужно `uv add max` и импорт
    `from max.algorithm import parallelize`. Статья написана до 1.0.
  </QuizItem>
</Quiz>
